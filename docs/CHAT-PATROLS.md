# In-Chat Patrols & Timers (`chat_patrol`)

**Status:** shipped 2026-10-28.

## Overview

Traders and operators often want their assistant to stay on patrol inside an active chat conversation — checking deal pacing, margin anomalies, backfills, or refreshing Pages dashboards every few hours (or waking up after a one-shot delay) with the conversation's full transcript, workspace files, Python variables, and enabled MCP connectors preserved.

Previously, recurring work required promoting a conversation to a standalone headless job in the Operations Center (`schedule_task`), where each occurrence starts in a fresh transcript outside the chat thread. In-chat patrols (`chat_patrol`) complement Operations Center tasks by scheduling recurring cron turns or one-shot timers directly on a `conversations` row.

## Shipped Architecture

1. **Persistence and firing (`sched` migrations `076_chat_schedules` and `077_move_chat_schedules`, `087_input_queue_patrol_mode.sql`, `088_input_queue_patrol_mode_validate.sql`, `internal/store/chat_schedules.go`, `internal/sched/db/chat_schedules.go`, `internal/sched/scheduler/chat_schedules.go`)**
   - Since #2049 M5 ([ADR-0104](adr/0104-one-scheduler.md)) the rows live in the scheduler's schema (`sched.chat_schedules`, moved from `chat.chat_schedules` by sched migration 077) and are fired by the scheduler's one tick loop, not a chat-side sweeper.
   - `chat_schedules` stores per-conversation recurring cron patrols (`cron_expr` with `MinChatPatrolCronInterval = 5m`, validated across 48 consecutive firings) and one-shot delay timers (`duration_seconds` between 10s and 30d), up to `MaxActiveSchedulesPerConversation = 5`.
   - Creating a recurring cron patrol on a conversation that already has an active or paused recurring patrol updates the existing patrol in place by default (`AllowMultiple = false`), preventing accidental duplicate patrols when adjusting cadence or instructions.
   - `SweepExpired` exempts conversations that hold an active or paused schedule in `chat_schedules` so long-running patrol threads are never reaped while active.
   - Each fire is claim → delivery → settle. The scheduler leases a due row (`lease_owner` / `lease_expires_at`, the tasks' lease model); the chat server's `DeliverChatScheduleFire` enqueues a `chat_input_queue` row with server-owned `mode = 'patrol'` (`store.InputModePatrol`) under the idempotency key `chat-patrol:<id>:<run>:<s|m>-<fire_id>` (s scheduled, m Run now). Patrol provenance is the queue row's server-owned `mode = 'patrol'` in the schedule's conversation, never the caller-supplied key alone: a user input that borrows a `chat-patrol:` key neither blocks nor counts as a patrol turn, and isn't cancelled with the schedule; the settle advances `run_count` / `next_run_at` / `status`, releases the lease and, for a fire that ran (`queued`) or was turned away (`busy`, `gone`), appends a row to `sched.chat_schedule_runs` (the run history, pruned with task runs by `FLEET_RUN_LOG_RETENTION_DAYS`); a Run now that coalesces onto a turn in flight (409) or is refused on a full queue (429) adds none. A fire that dies before it settles (or whose delivery failed, after a backoff) is re-claimed as itself by the recovery pass when its lease expires, whatever the schedule's status, and its re-delivery finds its own queue row. Pausing or cancelling a schedule revokes a fire in flight. Deleting a conversation deletes its schedules and their run history: a trigger on `chat.conversations` that sched migration 077 creates (and its down removes). On a database the scheduler initialised first, 077 found no chat schema, so `fleet serve` installs the trigger once both schemas exist — retrying in the background (5s doubling to 5m) for as long as the process runs if that fails — and the install removes every schedule orphaned until then. Once the trigger is in, deleting a conversation never leaves its schedules behind; until it is in, orphaned rows are inert (a fire of one finds its conversation gone and cancels it) and are removed by the install. **Run now** takes the same path through `Scheduler.RunChatScheduleNow`. If the conversation already has a queued or running patrol turn, a pending non-preview approval card, or a full input queue, due schedules coalesce and advance `next_run_at` (recurring patrols to the next cron tick; one-shot timers by 30s) so blocked schedules never pile up or starve later conversations. A scheduled fire turned away this way records why on its `busy` history row (`reason`, migration 0203: `patrol_in_flight`, `approval_pending` or `queue_full`; `''` for any other outcome and for rows recorded before 0203).

2. **Turn Execution, Approvals & Python State (`internal/httpapi/`, `internal/tools/`)**
   - Draining a `mode = 'patrol'` queue row launches a governed chat turn with `inputKind = agent.InputKindChatPatrol` (`"chat_patrol"`), rendered in the transcript as a collapsible `PatrolTurnNotice` card rather than a user bubble.
   - The interactive `chat_patrol` tool (`create`, `list`, `update`, `pause`, `resume`, `cancel`) lets the assistant manage the current conversation's schedule in-turn and emits `patrol.updated` SSE events so the UI updates live.
   - Model-callable `chat_patrol` never elevates `conv.AutoApprove` without explicit user consent; only user-authenticated HTTP requests (`POST /api/conversations/{id}/schedules` or `PATCH /api/conversations/{id}`) can enable `conv.AutoApprove`.
   - A patrol turn keeps `show_ui`, so it can draw cards and refresh [dashboard](DASHBOARD-VIEW.md) panels; in a multiplayer chat every participant sees them. When the chat has board cards, the turn's injected context lists them (title, card id, panel key and how to update each), so a run updates the existing panels instead of adding new ones even after a compaction; in a multiplayer chat its replay is the whole chat's history, other participants' turns included. A patrol turn never arms the Autonomous 10-second auto-submit countdown on a card it shows, and it is not offered `enable_mcp_connectors`.
   - When a patrol turn stages a critical tool approval card while `conv.AutoApprove` is off, the card receives at least a 24-hour (`86400s`) expiry floor and automatically arms `resume_after_approval`, so approving the card later immediately resumes the patrol turn.
   - `python_bridge.py` automatically checkpoints and restores serializable user variables (`.fleet_python_state.pkl` in the conversation workspace) across turns and patrol runs, and persistent sandboxes scope their writable bind-mount to `<WorkspaceHostDir>/<convID>` and reap any detached non-kernel processes on turn release.

3. **Web UI (`PatrolBanner.tsx`, `PatrolsDialog.tsx`, `patrolBarPrefs.ts`, `PatrolSchedulePicker.tsx`, `patrolSchedule.ts`, `Composer.tsx`, `chat-experience.tsx`)**
   - **Patrols & timers** (`PatrolsDialog`) is where the chat page creates, edits and stops a patrol (the assistant's `chat_patrol` tool, the Patrol Launchpad and persona patrols still can too). **More options → Patrol & schedule** opens it, and so does the composer's clock once the chat has a patrol. With no patrol yet it opens straight on the **New patrol or timer** form (`PatrolForm`); otherwise it lists every armed or paused schedule with **Run now** and **Pause/Resume**, and a card expands to the approval mode, the run prompt, **Edit schedule & task** (the same `PatrolForm`, sent as `PATCH …/schedules/<sid>` with only the changed fields, so a label or prompt edit never re-arms the schedule) and **Remove patrol** / **Cancel timer**, which needs a second, confirming click. The form's presets are `Every 1h`, `Every 2h`, `Every 4h`, `Every 6h`, `Weekdays 9am`, `Daily 9am` and `Custom` under **Repeats**, and `In 30m`, `In 2h` and `Custom` under **Once (timer)**. A recurring `Custom` opens the visual schedule builder (`Every N hours`, `Every N minutes`, `Every day`, `Weekdays (Mon–Fri)`, `Specific days of the week`, time picker, IANA time-zone dropdown with `Custom zone`, live `describeCronExpression` preview, `Advanced cron` input). A timer `Custom` takes minutes or hours (up to 1440m / 168h).
   - The **Patrol bar** (`PatrolBanner`) sits above the composer: human-readable cadence (`formatScheduleCadence`), live countdown, run count, an approval-mode dropdown (switching an armed patrol to Autonomous asks once more inside the menu, before the Autonomous risk prompt), **Run now**, **Pause/Resume** and **Hide**. The bar has no stop control. Its old `×` cancelled the patrol (a `DELETE`), and a Raptive user clicked it expecting it to dismiss the bar (2026-11-17), so stopping moved into the dialog behind a confirm.
   - **Hide** folds the bar into the composer's clock (ringed while hidden, with a six-second **Patrol bar hidden · Undo** note). The choice is per browser and per conversation (`patrolBarPrefs`, guarded `localStorage`), not stored on the server, so another device still shows the bar. A hidden bar comes back while the conversation has a pending approval card, with **Review** to scroll to it, and the clock turns amber. Approvals are per conversation, so the note is shown on the schedule that ran last. The dialog's **Show bar above composer** switch shows a hidden bar again.
   - **Patrol on hold** (`PatrolSkippedNote`, rendered by `PatrolBanner` under each row): skipping a slot while an approval card waits on the owner is deliberate (a patrol never stacks turns behind an unanswered card), but the owner had no way to see it — a user's two-hourly patrol skipped its 12:00, 14:00 and 16:00 ET slots on 2026-11-18 behind a card staged at 10:00, with nothing on screen. `ListChatSchedules` now sets `skipped: {reason: "approval_pending", count, slots}` on an active recurring patrol whose run history ends in a streak of scheduled `busy` rows with reason `approval_pending` (or `''`, so a streak recorded before 0203 still shows), fired no earlier than the oldest card still pending; `slots` holds at most the newest six due times, oldest first. Every response that carries schedules (the conversation load, the schedules routes and the `patrol.updated` event the scheduler publishes after each settle) carries it, so the note appears as soon as a slot is skipped and goes once the card is answered. The bar shows the skipped times in the viewer's zone (`Tue` added for a slot on another day). Not covered: one-shot timers (a busy timer retries every 30s instead of skipping a slot) and slots skipped for a patrol turn still in flight or a full queue, which are recorded but not shown. The read is display data: if it fails, the schedules are returned without it.
   - The approval mode is the conversation's (`approval_mode`), not per schedule, so the bar shows the dropdown once and the dialog notes that it applies to every patrol in the chat.
   - The page polls while a patrol is active, so background patrol turns stream into open tabs automatically.

## Deferred Scope

- Cross-conversation patrol dashboards (listing all active chat patrols across every conversation on one admin screen) are deferred; Operations Center remains the board for fleet-wide scheduled jobs.
