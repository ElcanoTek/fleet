# Feature design notes

Per-feature implementation notes moved out of `AGENTS.md` (issue #527) so the
agent operating guide stays lean. Each bullet is the shipped design summary for
one feature — including its **deviations from the original issue and honest
scope** — written when the feature landed. Newer features usually also have a
dedicated page in `docs/` and an ADR in `docs/adr/`; for the ones that don't,
this file is the canonical design note.

When you ship a feature: put the design note in a dedicated `docs/<FEATURE>.md`
(plus an ADR when it adds or changes an invariant) and a `CHANGELOG.md` entry.
Only add a bullet here if the feature is too small for its own page — and never
add feature notes back into `AGENTS.md`.

- **Save a chat to the prompt library**: the conversation kebab gains "Save to prompt library…" next to "Make recurring task…" (#455's sibling). `POST /conversations/{id}/suggest-prompt` (`internal/httpapi/suggest_prompt.go`) reuses `transcriptFromHistory` and a new synthesizer `(*agent.Manager).SuggestLibraryPrompt` (`internal/agent/library_prompt.go`, `FLEET_LIBRARY_PROMPT_MODEL`, structuredoutput `{name,description,content}` — same pattern as `SuggestRecurringTask`, returns an ERROR not nil since it's user-initiated) to distill the refined ask out of a meandering conversation (keeps the most-recent 12K runes). DELIBERATE split: the chat server only synthesizes and returns the draft; persistence happens client-side through the orchestrator's existing `POST /prompts` after the user reviews/edits it in `SavePromptDialog.tsx` (private by default, workspace opt-in) — so there is no second write path into `prompt_library` and `PermissionCreateTask` gating applies unchanged. A failed distillation offers Retry instead of an empty form; Cancel persists nothing.

- **Input queue + mid-turn steering (#785)**: `registerTurn` now REFUSES while a turn runs (no implicit cancel); busy submissions become durable `chat_input_queue` rows (migration 042; idempotent on `(conversation, client_input_id)`) acknowledged with 202 JSON, drained FIFO via DB-atomic SKIP LOCKED claims kicked by enqueues + turn-completion tail calls (no per-conversation goroutine); `startTurn` extraction shares the full launch path (governance unchanged) between direct and drained turns. Steering: `agentcore.Deps.SteerSource` + `steeringStep` chained FIRST in PrepareStep (budget-accounted, append-only for the prompt-cache prefix, between-steps only), ack-gated durable queued→injected flip, `user_text` sink entries deduped by SteerID across resilience re-drives, persisted exactly once via the #798 commit (`CompleteInjectedInputs` post-commit), queued-turn fallback otherwise. Stop (`/cancel`) covers queued rows (`scope=all` default). Boot `RecoverInputQueue` resolves claimed/injected rows against the #798 record and never auto-drains. Web: queue chips + send-now/remove, steered user bubbles, queue-while-streaming composer. Docs: docs/INPUT-QUEUE.md. Honest scope: steer is text-only (attachments downgrade to queue), no reorder beyond promotion, scheduled runs unaffected.
- **Durable turn journal + gated terminal success (#798)**: interactive turns commit the user entry (`Store.CommitUserMessage`, `(turn_id, turn_seq=1)` provenance) BEFORE the first provider call; every tool route journals intent pre-dispatch (fail closed) and the exact #793-governed model-visible result post-boundary via the nil-safe `agentcore.Deps.TurnJournal` seam (`httpapi.turnJournalWriter`: bounded retry, degraded latch blocks further dispatch AND terminal success); `turn.completed`/`turn.cancelled` gate on `Store.CommitTurnHistory` (FOR-UPDATE guard, `ErrTurnHistoryCommitted` absorbs ambiguous-commit retries) — a failed commit is a visible `turn.error`, never a vanishing answer. Boot-time `RecoverStrandedTurns` projects crashed turns into one explicit interrupted turn (journal-authoritative pairing; synthesized unknown-outcome results marked `synthesized=TRUE` for reconciliation; best-effort text from `turn_events` with `turn.retry` rollback; idempotent via the `messages_turn_seq` partial unique index). Migration 041. Docs: docs/TURN-JOURNAL.md + ADR-0039. Honest scope: no late re-projection of alive-but-unpersisted turns, no per-step usage checkpointing (recovered turns have zero-usage summaries), no per-tool idempotency classes, scheduled runs unchanged.
- **Governed lifecycle hooks (#788)**: bundle-declared `hooks:` (clientconfig `HooksConfig`/`HookDef` + `validateHooks`, additive strict-YAML key) run at four lifecycle points via a per-run `agentcore.hookEngine` built in `Run` (nil/zero-overhead when none configured). `user_prompt_submit`/`turn_end` wire in run.go; `pre_tool_use`/`post_tool_use` wire into `policyGuardedTool.Run` (pre BEFORE `policy.BeforeToolCall`, post appended before `RecordToolResult`) and `mcpTool.Run` (fires under the real `mcp_<server>_<tool>` name — covers the deferred-disclosure route; bridge wrappers get `hooks:nil` to avoid double-fire). Hooks execute via the `Executor` seam (sandbox `RunBash`, never host exec), payload piped through `printf … | timeout Ns bash -c …` (in-container timeout = #796 leak mitigation), stdin JSON redacted+capped (no env/creds), stdout = last-JSON-line decision. Outcomes: continue / block-with-reason / bounded additional_context (per-fragment + 32 KiB per-run budget). enforce=true fails closed, advisory fails observable; panic-contained; every call emits a `hook.decision` observer event. Gates evaluate AFTER hooks on unmodified input (can only narrow). cmd/fleet `toAgentcoreHooks` + `ConfigureLifecycleHooks` install at startup. Docs: docs/HOOKS.md + ADR-0038. Honest scope: deferred pre/post_compact + subagent_start/end events, argument rewriting/"ask", hook hot-reload, turn_end on cancelled runs, multi-source discovery.
- **Sandboxed file tools + host-I/O audit (#784)**: `view_file`/`write_file`/`edit_file` now execute inside the per-turn sandbox via `Sandbox.RunFileOp` (container backend: one-shot `podman exec python3` over embedded `fileops.py`; host/test backend: the same script), inheriting the selected runtime/seccomp/caps/cgroups/disk/PID/network posture. The executor binds the narrow conversation/worktree root's in-runtime identity before tools run, checks it on every writable call, and then uses dirfd-relative no-follow traversal (deterministic interior-swap and whole-root-exchange coverage); atomic replacements preserve existing metadata, fsync the file/parent, and cancellation synchronously kills + retires the container. Supporting-document mounts are separate read-only capabilities. Host path validation remains defense-in-depth; nil sandbox fails closed; an untagged release build ships no host FileOp implementation. Scheduled non-worktree tools resolve against the workspace root. Governed large model outputs now use the same confined seam (#793): legacy host spills were removed, and post-governance recovery has 16 immutable workspace slots shared with sandboxed `view_file` for private conversation and isolated worktree roots; shared non-worktree scheduled roots remain cap-only because no task owns the root ([design](TOOL-OUTPUT-BOUNDARY.md)). Full host-I/O classification + the fixed control-plane/broker exceptions are in [ADR-0036](adr/0036-sandboxed-file-tools-and-host-io-exceptions.md). Honest scope: migrating legacy staging/read tools (`xlsx`, `download_url`, `generate_image`, `fastio_upload`, email materialization), a persistent in-container FileOp session, and auto-mounting `FLEET_ALLOWED_DIRS` are deferred; #787 builds ambiguity/stale/diff/batch edit semantics on this seam.
- **Audit-gate v1 parity: typed commitment binding, payload failures, create reconciliation (#715/#716/#717)**: three governance hardenings ported from the v1 engine into `internal/agentcore` before v1 retires; design + invariant wording in [ADR-0034](adr/0034-audit-gate-commitment-binding.md). Typed `confirm_audit` `critical_actions` entries bind to the full server-qualified tool name + optional `deal_id`/`deal_ids`/`values_digest` (wire field names kept verbatim — the bundles' protocols emit them; fleet treats the values as opaque record ids), fail closed on zero resolved commitments, and gate every critical call while active (`audit_commitment.go`); untyped audits keep the legacy suffix fallback (deliberate deviation: v1 now refuses legacy free text outright — fleet keeps it so existing bundles don't break, but it can never approve a `deal_ids` batch). Payload-level failures (`success:false` / top-level `error`) never discharge a commitment, superseding the `send_email`-only check for enforcement (the provider-specific `sendEmailSucceeded` still governs the send counter); per-record `results[]` discharge is idempotent and approved-set-scoped. Unresolved `creates.jsonl` pre-POST markers in the run's resolved MCP workspace are replayed as the v1-byte-compatible reconciliation block appended to the task prompt (never the cached system prefix). Honest scope: deliberately NOT ported — the v1 canary-then-apply batch gate, the sibling-wipe (full-object replacement) guard, and the abort-notification invariant (all v1-protocol-specific); and per-run MCP workspaces are freshly minted each run, so the reconciliation replay mainly protects shared-client deployments until #707 lands per-task-stable workspace granularity.
- **Per-task wall-clock timeout (#724)**: `FLEET_TASK_WALL_TIMEOUT` (Go duration; default 4h, `0` disables) bounds a scheduled run's total elapsed time. Enforced by the worker pool (`internal/runner`) around the run invocation — the issue said "the scheduler", but `internal/sched/scheduler` only promotes due tasks; the pool is where the run's context lives. Expiry cancels the run via `context.WithTimeoutCause` and fails the task terminally with a clear timeout error, classified BEFORE the retry branches so the transient-retry policy is never consulted (deterministic: a run that hit the ceiling once would hit it again). Honest scope: a global env knob only — deliberately NO per-task column/schema change (per-task expectations remain `expected_duration_minutes` for advisory SLA monitoring and loop `time_budget_seconds`).
- **Upload accepts scoped create_task keys (#719)**: `POST /v1/upload` now honors a scoped API key carrying create_task permission — the same authority the create paths validate (`ValidateKey`, one rate-limit token) — since an uploaded file is only usable via a subsequent create. Valid-but-under-scoped typed keys (readonly/webhook) get the create paths' definitive 403. Admin key / bearer / cookie paths byte-for-byte unchanged.
- **Create-time persona validation (#720)**: an unknown non-empty `persona` on task create is now a 400 listing the bundle's valid persona names (was: silent fallback to the global default at dispatch, so a typo produced wrong-persona runs with no error). The handlers stay decoupled via an injected `SetPersonaCatalog` seam that reads the bundle personas dir live per call (hot-reload safe). The dispatch-time fallback is kept deliberately: a bundle can drop a persona AFTER a task was created, and such a task still runs on the global default. `docs/openapi.yaml` TaskCreate also gained the previously-undocumented `name`, `persona`, `credential_allowlist`, `tags`, `timezone`, `description`, `max_retries`, `carry_context` fields.
- **CLI parity round (#722)**: `fleet sched task list` (default columns: short id, name/prompt excerpt, status, priority, recurrence/scheduled_for, model; `--status`, `--limit`, `--json`); `fleet sched apikey create --rate-limit-per-minute` names the unit (`--rate-limit` remains a deprecated alias that warns — v1's flags were per hour); `fleet start` alongside stop/restart; the fleet-admin shim's `task run` now errors with "use the unified fleet binary" instead of a generic unknown-subcommand; top-level help gained the shipped-but-unlisted verbs (sched trigger/dlq, apikey rotate, task memories, sched task list, start). Honest scope: NOT done from the issue's smaller-gaps list — multi-unit `fleet logs`, changing bare `fleet` to print help (deliberate: ADR-0012 keeps bare `fleet` booting the daemon so a historical systemd unit can't brick), and a git-backed user-memories backup.
- **Unified settings area**: every settings surface renders inside one shared shell (`web/src/app/settings/SettingsShell.tsx`) — brand row, an Operations Center cross-link + "Back to chat" pill, and a section nav (General · Connections · Skills · Admin) with the active page marked. The Operations Center's Settings **modal** was retired: its content (concurrency cap + MCP credential accounts) moved to the new `/settings` (General) page, whose components live in `web/src/app/settings/`. The account menu offers Settings/Connections/Skills/Admin identically on both surfaces (no more per-surface forks); the orchestrator proxy accepts the same session, and authorization stays enforced upstream. The Admin tab is visible to everyone — the page itself is allowlist-gated server-side, exactly like the account-menu item before it. Honest scope: the General page's two panels are moc-heritage — the fleet orchestrator serves neither `PUT /concurrency` nor credential-account create/delete (`fleet mcp account set` is the CLI path), so those writes only function when `ORCHESTRATOR_SERVER_URL` fronts a moc backend; against fleet's own orchestrator they surface an error toast, exactly as they did in the old modal.
- **`fleet update` deploys the web build**: `scripts/update.sh` used to rebuild the Next app in the source checkout but never copy it into the `fleet-web` unit's WorkingDirectory (`/opt/fleet/web`) nor restart `fleet-web` — the live site kept serving the old bundle after every update. It now rebuilds with the `NEXT_PUBLIC_*` stamps grepped from `/etc/fleet/fleet-web.env` (client-visible values only; the 0600 file is still never sourced), deploys to the unit's WorkingDirectory, and restarts `fleet-web` after the backend comes back.
- **Composer & Textarea heights**: In `web/src/app/chat/ui/Composer.tsx` and `chat-experience.tsx`, avoid mixing JS-based auto-grow style height clamping with Tailwind `max-h-*` CSS classes on the composer textarea, to prevent layout flickering. Use `MAX_COMPOSER_HEIGHT_PX` (200px) as the single source of truth.
- **Composer keybindings & preferences**: The user's send preference (`fleet.sendKey` in localStorage) controls whether Enter or Ctrl+Enter (with Cmd+Enter) sends a message. The keydown handler adjusts based on this config and skips sending on touch devices to let mobile keyboards use native enter keys.
- **Bulk Conversation Operations**:
  - **Soft Delete**: Setting `FLEET_CONVERSATION_SOFT_DELETE=true` switches deletes to soft-deletes (`deleted_at` timestamp). A 30-day background sweeper permanently purges soft-deleted rows. Soft-deleted conversations are excluded from retrieval and search query filters.
  - **Bulk APIs**: Bulk delete and patch actions are rate-limited to 100 IDs per request. Transactional pre-checks protect ownership; any single foreign ID fails the entire request (403 forbidden) to ensure consistency.
  - **Bulk UI**: Uses checkboxes for selection, warning users when selecting more than 50 conversations. The confirmation modal enforces a 3-second disabled countdown for delete actions.
- **Conditional Task Execution (run_if)**:
  - Pre-run shell gates (`run_if`) are evaluated serially on the host as the fleet process user prior to task promotion.
  - The evaluation is restricted to `PATH=/usr/bin:/bin` and `HOME=/tmp` with a custom timeout.
  - Only admins may create or change a gate. Captured stderr is capped at 8 KiB
    (with an explicit truncation marker), so a noisy command cannot grow the
    scheduler process heap until its timeout.
  - If a gate skips a recurring task, its status stays `scheduled`, and `scheduled_for` is advanced to the next cron occurrence. For one-shot tasks, status remains `scheduled` but the time is not advanced, acting as a soft hold.
- **Batch Task Operations**:
  - **Batch APIs**: `POST /tasks/batch` allows batch task creation of up to 100 tasks. In atomic mode (`atomic: true`), all tasks are validated up front and created in a single DB transaction (returning `422 Unprocessable Entity` with errors if any fail). In non-atomic mode (`atomic: false`), it behaves best-effort and returns `207 Multi-Status` for partial success.
  - **Rate Limiting**: Rate limiter consumes `N` tokens for `N` tasks in a batch (instead of 1 token per batch request) via `apikeys.Manager.ConsumeN`.
  - **Single Multi-row Insert**: `db.AddTaskBatch` inserts multiple tasks in a single query via parameterized multi-row insert rather than individual sequential inserts.
  - **CLI**: `fleet task batch-create --from-file tasks.json [--atomic]` allows creating tasks from a JSON file (or stdin via `-`).
- **Task Definition Import/Export**:
  - **Task Names**: Scheduled tasks now support an optional `name` field (mapped to the database `tasks.name` column with a partial unique index). Empty/empty-string names represent "unnamed" tasks and are always created fresh on import. Non-empty names are unique and serve as conflict keys.
  - **Payload Limits**: Imports are rate-limited/capped to at most 100 task records per request (matching bulk API policies). Payload-internal duplicate name entries are validation errors.
  - **Conflict Behaviors**: Mode `conflict=error` aborts the batch on any collision; `conflict=skip` skips colliding entries and writes others; `conflict=replace` performs an in-place update of colliding entries. Mode `conflict=replace` requires admin permission.
  - **Formats**: Support both JSON and YAML envelopes (via `github.com/goccy/go-yaml`). Version is set to `"1"`.
- **Read-only conversation sharing (#226)**:
  - **Opt-in public links**: `POST /conversations/{id}/share` mints a 256-bit `crypto/rand` (base64url) token stored in `conversations.share_token`; `DELETE` revokes it. `GET /shared/{token}` returns a read-only snapshot (title/model/messages) that **deliberately omits the conversation id and owner email**. Optional `share_expires_at` is enforced server-side.
  - **Public-but-proxied**: `/shared/{token}` is token-only-gated (shared secret — only the Next proxy reaches it, not the open internet) and IDENTITY-less; the share token is the authorization, token entropy is the confidentiality guarantee, and a per-TOKEN rate limit (`shareRL`, 120/min) is the abuse gate (per-IP would see only the proxy). The Next page `/shared/[token]` is account-less (middleware bypass) and fetches via `chatServerFetchPublic` (secret, no user email).
  - **Sweep exemption**: `SweepExpired` skips `share_token IS NOT NULL` rows (TTL delete + per-user cap) so a live share link is never silently revoked by retention.
- **Task Priority Queues (#230)**:
  - **Convention**: `priority` is an integer in `[0, 100]` where **lower = more urgent** (POSIX `nice`-style). The Go zero value (`0`, i.e. unset) is normalized to `models.PriorityNormal` (50) by `models.NewTask`; named reference points live as `models.Priority{Critical,High,Normal,Low,Bulk}` constants. Validated in `validateTaskLimits` and by a DB `CHECK`.
  - **Two columns**: `priority` is the immutable submitted value; `effective_priority` is what the claim path orders by (`ORDER BY effective_priority ASC, created_at ASC`). They are equal at creation. `effective_priority` is **write-once at INSERT** — it is deliberately excluded from the `AddTask` upsert/`ON CONFLICT` (and `UpdateTask` delegates to `AddTask`), so a status update with a stale in-memory copy can never clobber a promotion. The ONLY mutator afterward is the anti-starvation sweep.
  - **Anti-starvation**: a per-tick scheduler sweep (`PromoteStarvedTasks`) raises the `effective_priority` of pending tasks waiting past `FLEET_TASK_STARVATION_WINDOW_MINUTES` (default 30; `0` = off) to `StarvationFloorPriority` (High, never Critical), so a stream of urgent work can't starve a low-priority task — without rewriting its submitted `priority`.
  - **Per-key cap**: a scoped API key's optional `MaxPriority` (JSON-persisted on the key, not a DB table) makes both `POST /tasks` and `POST /tasks/batch` reject any task more urgent (lower) than the ceiling (`403` / per-task batch failure), via the shared `priorityCapError` helper so the two create paths can't drift.
  - **Inspection**: admin-only `GET /admin/queue` returns per-tier pending depth + oldest-pending age.
  - **Deviation from the issue**: named tiers are Go constants and the window is an env var (matching the existing retention/archival knobs), NOT a `manifest.yaml` map — server scheduling policy stays out of the external client bundle.
- **Conversation Folders & Labels (#258)**: builds on the `folder TEXT`/`labels TEXT[]` columns + bulk-mutation from #279.
  - **Filtering**: `GET /conversations?folder=&label=` filters the list — `?label=` is repeatable with **AND** semantics (Postgres `labels @> ARRAY[...]`). Backed by `store.ListFiltered(ctx, user, ListFilter{...})`; the old `List(ctx, user, archivedOnly)` now delegates to it. The query is a **constant string with sentinel-guarded clauses** (`$N IS NULL OR …`, mirroring `DeleteAllMatching`) — no SQL concatenation. `folder` is `NOT NULL DEFAULT ''`, so `''` is the explicit "no folder" bucket (a `*string` pointer to `""` filters for it; `nil` = no folder filter).
  - **Enumeration / rename**: `GET /folders` → `[{name,count}]` (distinct non-empty folders, active only); `POST /folders/rename {from,to}` is a single bulk UPDATE (no folders table — a folder IS the set of conversations naming it). Both scoped by `user_email`.
  - **Validation** (`normalizeAndValidateFolderLabels`, HTTP layer): ≤10 labels, ≤32 chars each (trimmed, non-empty), folder ≤64 chars; applied on the bulk PATCH path — this is the **server-side** enforcement of the bounds the UI already applies client-side, closing a gap left by #279's unvalidated bulk mutation. Empty folder (`""`) is allowed = clear.
  - **UI** is owned by #169 (the unified NavRail shell): `conversationOrganization.ts` derives folders/labels **client-side** from the loaded list and renders the organized Pinned·Folders·Labels·Recent list + label chips + kebab folder/label panels. This issue's server-side filtering/enumeration/rename endpoints are API capabilities (matching the #258 spec) the bundled UI doesn't need to call, since it filters client-side.
- **Per-task Sandbox Limits (#205)**: a task may override the global `FLEET_SANDBOX_*` cgroup ceilings.
  - **Model**: `TaskSandboxLimits{MemoryMB, CPUs, Pids}` (a zero field = use the global default), stored as the nullable `sandbox_limits` JSONB column (migration 040; NULL = all-global). Threaded through `db.go` exactly like `loop_config` (taskColumns/scanTask/AddTask/taskInsert\*/UpdateTaskTx) and the export/import record.
  - **Validation** (`Handlers.validateSandboxLimits`): floors (≥128 MiB, cpus>0, ≥16 pids) and operator ceilings `FLEET_SANDBOX_{MEMORY_MAX_MB,CPUS_MAX,PIDS_MAX}` (defaults 8192/16/1024; 0 = uncapped), surfaced onto `handlers.Config`.
  - **Application**: per-task limits require a COLD start (a warm pooled container already runs with the pool's ceilings). `takeTaskSandbox` routes a task with non-zero `SandboxLimits` through the new `Pool.TakeContainerWithOverrides(ctx, ResourceOverride, noNetwork)` — applying the override to a copy of the pool config (`ResourceOverride.applyTo`, the testable seam for the `--memory/--cpus/--pids-limit` values) and keeping the task's network posture (sealed unless `AllowNetwork`). `TakeContainer` now delegates to it. A tightening of the mandatory sandbox, never an escape.
  - **Deferred** (honest scope): the `fleet task set-limits` CLI and the web "Advanced settings" panel — per-task limits ship usable now via `POST /tasks` and `fleet task import` (the JSON/YAML carries `sandbox_limits`).
- **Agent delegation (#175 + #264)**: a scheduled run can delegate scoped subtasks to governed CHILD runs via the `spawn_subagent` native tool (this one tool is the delegation primitive #264 asked for — NOT a separate `delegate_task`; a second tool would fork the one governed core). See [`docs/adr/0007-governed-sub-agents.md`](adr/0007-governed-sub-agents.md).
  - **Opt-in**: per-task `allow_delegation: true` OR fleet-wide `FLEET_SUBAGENTS_ENABLED` (composed as OR in `scheduledrun`); registered ONLY in scheduled mode, never interactive. Off by default → byte-for-byte unchanged. `allow_delegation` is threaded like `allow_network` (migration 041, taskColumns/scanTask/AddTask/taskInsert\*/UpdateTaskTx, export/import, rerun overrides).
  - **Parallel**: the tool is `NewParallelAgentTool`, so multiple `spawn_subagent` calls in one model turn run concurrently (fantasy's parallel-tool semaphore, cap 5) and results fan back in before the next LLM call. Output is JSON `{result, cost_usd, tokens, success}`. The atomic budget reservation (under the parent `mu`) makes concurrent spawns safe; `make test-race` covers it.
  - **Governance**: child runs through the SAME `agentcore.Run`; budget is capped at `FLEET_SUBAGENTS_BUDGET_FRACTION` (default 0.10 = ≤10% of the parent's remaining, a request over the cap is REFUSED) and charged back to the parent; `FLEET_SUBAGENTS_MAX_DEPTH` default **1** ("parent → sub-agent only" — a child is built without the tool); `FLEET_SUBAGENTS_MAX_CHILDREN` default **5** (the 6th spawn returns a "max concurrent sub-agents reached" error result). Optional `timeout_minutes`/`max_iterations` per child; `parent_task_id` links a child's run to its owning task.
- **LLM git-metadata tools (#191)**: three native tools let an agent self-document the code it produces — `suggest_branch_name`, `suggest_commit_message`, `suggest_pr_description` (`internal/tools/metadata_tools.go`).
  - **Pattern**: each mirrors `SuggestTitle` (`internal/agent/title.go`) — a short-lived `fantasy.NewAgent` call with a tight system prompt and a 20s timeout, resolved through the SAME host-side `ModelResolver` the run already uses. The operator's key stays host-side and never enters the sandbox; the call rides the shared governed provider, not a bare HTTP request.
  - **Validation**: model output is validated before it is returned — branch names against `^[a-z][a-z0-9/-]{1,59}$` (plus a guard rejecting `//` and a trailing `/` that the class alone allows but git refuses), commit subjects against the Conventional Commits header + ≤72 chars, PR descriptions for the required `## Summary` section. A branch name is thus never an unsafe ref handed to git; the commit *body* and PR description are returned as free-form text/markdown (only their header is validated), which is safe because the agent consumes them inside the mandatory sandbox — these tools never interpolate output into a host-side shell. The validators are pure functions (`normalizeBranchName`/`normalizeCommitMessage`/`normalizePRDescription`), unit-tested without a live model.
  - **Config**: `FLEET_METADATA_MODEL` (a `MetadataModel` field on `config.Config`), defaulting to `FLEET_TITLE_MODEL`'s value — zero new required config.
  - **Scoped to the scheduled native set**: wired via `tools.MetadataTools(r.mgr, metadataModel)` appended in `internal/scheduledrun`, NOT in the shared `tools.NewTurnTools`/`DefaultTools`. Rationale: autonomous scheduled agents that produce branches/commits/PRs are the use case, and a task's MCP selection is narrow, so the 3 always-on tools stay clear of the 128-tool request ceiling — whereas the interactive chat turn runs near that ceiling once per-user remote MCP servers (#449) load, and CI (which uses the 0-MCP default bundle) can't catch an over-128 overflow. `TestMetadataTools_NotInSharedTurnSet` locks this so any future re-addition to the shared set is a deliberate, reviewed decision.
  - **Deviation from the issue** (honest scope): (1) the issue wires these into `DefaultTools()`/`NewTurnTools()` for all native flavors; we scope to scheduled-only for the ceiling reason above (interactive chat does not need an LLM to name a branch — a human is present). (2) The issue describes excluding the tools from an external/containment "acp" flavor in `buildFantasyTools`, but no such ACP runtime exists in this codebase. (3) A single `FLEET_METADATA_MODEL` is used (per the issue), not three per-tool model knobs.
- **Client SSE capability negotiation (#194)**: a client can declare which SSE event classes it handles so the server suppresses the rest (`internal/httpapi/capabilities.go`).
  - **Wire protocol**: the client sends `X-Fleet-Capabilities: ["text","tool_calls",…]` (a JSON array) on `POST /chat` and the stream-reattach `GET`; the server replies with `X-Fleet-Supported-Capabilities` and emits a synthetic `fleet.capabilities` event as the **first** SSE frame (no `id:` line, not persisted — like `reconnect`/`heartbeat`) so a header-blind `EventSource` can still discover support.
  - **Filtering**: `shouldEmit(caps, name)` gates both the live `turnBuffer.Attach` path and the DB-fallback `replayEventsFromDB`. Only events in `capabilityForEvent` are gated (`text.delta`→`text`, `reasoning.*`→`reasoning`, `tool.call`→`tool_calls`, `tool.result`→`tool_results`, `tool.approval_*`/`tool.auto_resolved`/`memory.proposed`→`approval_cards`). **Lifecycle/control frames always flow** (`turn.*`, `conversation*`, `user.message`, `status`, `reconnect`, `buffer_expired`, `fleet.*`) so a filtering client can't break turn-state tracking.
  - **Backward compatible**: no header (or malformed) → `parseClientCapabilities` returns `nil` → no filter → the full stream, exactly as before. Unknown tokens are ignored. The bundled web client sends no header and treats unknown event names as no-ops (chain of `if event.event === …`), so it is unaffected.
  - **Deviation from the issue** (honest scope): only capabilities for events that ACTUALLY emit here are advertised — `text`, `reasoning`, `tool_calls`, `tool_results`, `approval_cards`.
